## Not Yet Done

### ThumbnailLoader Cancellation Slot Accounting

Status: complete.

`RawCull/Actors/ThumbnailLoader.swift` no longer treats every continuation resume as a granted concurrency slot. Slot acquisition is now explicit: `acquireSlot()` returns an internal `SlotAcquisition` result instead of `Void`.

```swift
private enum SlotAcquisition {
    case granted
    case cancelled
}
```

Pending continuations now resume with that result:

```swift
private var pendingContinuations: [
    (id: UUID, continuation: CheckedContinuation<SlotAcquisition, Never>)
] = []
```

The immediate path increments `activeTasks` and returns `.granted`. A cancelled task returns `.cancelled` without incrementing. `removeAndResumePendingContinuation(id:)` resumes cancelled waiters as `.cancelled`, and `cancelAll()` drains queued waiters the same way.

`releaseSlot()` now transfers an existing active slot directly to the next waiter instead of decrementing first and expecting the resumed waiter to increment later. That keeps `activeTasks` bounded during the handoff window where a fresh caller could otherwise observe capacity and over-admit work.

`thumbnailLoader(file:targetSize:)` now installs `defer { releaseSlot() }` only after acquisition returns `.granted`. Cancellation-only wakeups return `nil` without releasing a slot that was never acquired.

Debug-only actor hooks were added for tests:

- current active slot count
- pending waiter count
- configured max concurrency
- max observed active slot count
- direct acquire/release helpers for slot-accounting tests

Added test file:

- `RawCullTests/ThumbnailLoaderConcurrencyTests.swift`

Covered cases:

1. Saturated loader queues a waiter until a slot is released.
2. Cancelled queued waiter does not consume a slot.
3. Max-concurrency bound holds while queued waiters cancel and resume.
4. `cancelAll()` drains waiters without granting slots.
5. FIFO grant skips a cancelled middle waiter.

Verification command:

```bash

```

Result:

```text

```

Acceptance criteria:

- Cancellation cannot over-admit work.
- `activeTasks` only counts real granted slots.
- A cancelled queued waiter never causes a slot increment.
- `cancelAll()` drains pending waiters without granting decode work by accident.
- Tests prove active slot count remains bounded at `maxConcurrent` across saturation, cancellation, normal release, and `cancelAll()`.

### Cancellation-Aware Sony/Nikon Thumbnail and JPEG Extraction

Status: complete.

These files now route ImageIO work through `CancellableImageIOWork`:

- `RawCull/Enum/SonyThumbnailExtractor.swift`
- `RawCull/Enum/NikonThumbnailExtractor.swift`
- `RawCull/Enum/JPGSonyARWExtractor.swift`
- `RawCull/Enum/JPGNikonNEFExtractor.swift`

`CancellableImageIOWork` wraps the GCD handoff with `withTaskCancellationHandler`, an `ImageIOCancellationToken`, and locked single-resume continuation state. Cancelling the outer task marks the token and resumes the caller with `CancellationError`; JPEG extraction APIs convert cancellation to `nil`.

The extractors cooperatively check cancellation before expensive phases:

- before source creation
- before ImageIO index scans
- before decode/downsample calls
- before cache eviction loops
- before Sony/Nikon binary fallback location reads
- before embedded JPEG data reads and fallback thumbnail decode

`CGImageSource` and `CGImage` values remain local to the synchronous ImageIO worker closure. No `@preconcurrency` imports were introduced.

Added test file:

- `RawCullTests/CancellableImageIOWorkTests.swift`

Covered cases:

1. Cancelled ImageIO work resumes without running the decode phase.
2. Cancelled Sony thumbnail extraction throws `CancellationError`.
3. Cancelled Nikon thumbnail extraction throws `CancellationError`.
4. Cancelled Sony JPEG extraction returns `nil`.
5. Cancelled Nikon JPEG extraction returns `nil`.

### Await In-Flight Sharpness Scoring Before Similarity/Burst Actions

Status: not done.

`SharpnessScoringModel.scoreFiles(_:)` still returns immediately when `isScoring` is true:

```swift
guard !isScoring, !files.isEmpty else { return }
```

`SimilarityGridSelectionView.runWithAutoScoring` still calls `await viewModel.calibrateAndScoreCurrentCatalog()` when scores are empty, but it does not await an already-running scoring task. A rapid second action can still proceed while the first scoring run is active.

Remaining work:

1. Make scoring awaitable when a scoring task is already in progress.
2. Return the existing task's value instead of returning early.
3. Make auto-scoring actions wait for actual completion.
4. Disable or mark similarity/burst controls while the prerequisite is running.

Acceptance criteria:

- Similarity and burst grouping cannot bypass required sharpness scoring.
- Existing scores are reused.
- In-flight scoring is awaited exactly once.

Remaining work:

Acceptance criteria:

- Cache-write lifetime is explicit.
- No non-Sendable image object crosses into detached save work.
