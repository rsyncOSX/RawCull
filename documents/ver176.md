## Release Objective

v1.7.6 should be a stability, correctness, and release-readiness update rather than a broad feature release.

RawCull already has meaningful functionality in place: catalog scanning, Sony/Nikon raw support, focus point parsing, thumbnail caching, sharpness scoring, similarity indexing, burst grouping, culling persistence, and rsync-based copy/export. The next version should reduce risk in the parts that can hurt real culling sessions: cancellation, memory pressure behavior, long-running image extraction, stale async work, test command drift, and repeatable release builds.

### 2. Correct Test Documentation and Smoke Test Invocation

Motivation:

The repository documents `xcodebuild test -scheme RawCull -testFilter smoke`, but the installed `xcodebuild` rejects `-testFilter`. This creates false confidence in the test process and slows every release check.

Current gaps:

- This machine is using Xcode 26.5 (`17F42`).
- `xcodebuild -help` on this machine supports `-testPlan`, `-showTestPlans`, `-only-testing`, `-skip-testing`, `-only-test-configuration`, and test enumeration, but not `-testFilter`.
- `xcodebuild -showTestPlans -project RawCull.xcodeproj -scheme RawCull` currently reports a local `RawCull` test-plan association, but there are no committed `.xctestplan` files in the repository.
- The Swift Testing tags exist in source (`.smoke`, `.performance`, `.critical`, `.threadSafety`, `.integration`), but the repository has no committed command-line bridge from those tags to `xcodebuild`.
- No `.xctestplan` file is checked in, so there is currently no committed smoke/performance test-plan configuration.
- No shared `.xcscheme` file is checked in; only user scheme metadata exists under `xcuserdata`. `xcodebuild -list -project RawCull.xcodeproj` can see the `RawCull` scheme on this machine, but the release docs should not rely on uncommitted user-local scheme state.
- The Makefile has release/debug build targets, but no canonical test targets.
- The stale command appears in at least `AGENTS.md`, `CLAUDE.md`, and `RawCullTests/TEST_ARCHITECTURE.md`.
- `-only-testing:` can select suites or test identifiers, but it is not tag filtering. If used, the smoke subset must be explicitly listed and maintained.

Accepted test patterns:

- Unit and integration tests should use Swift Testing, not XCTest.
- Test suites should prefer `struct` types. Use `@Suite` only when naming the suite or attaching suite-level traits.
- Tests should use `@Test`, `#expect`, `#require`, `Issue.record()`, and precise `#expect(throws:)` checks instead of XCTest assertions.
- Define category tags with `extension Tag { @Tag static var ... }` and apply them through `.tags(...)`.
- Keep tests isolated, repeatable, self-verifying, and order-independent because Swift Testing can run tests in parallel.
- Prefer parameterized tests when they reduce repetition without hiding intent.
- New feature or bug-fix coverage should include the relevant happy path, boundary, invalid-input, and concurrency scenarios.

Plan:

1. Verify the local build/test environment before treating source failures as release blockers:
   - Confirm the Metal Toolchain is installed. If build-backed tests fail with `cannot execute tool 'metal'`, install it with `xcodebuild -downloadComponent MetalToolchain`.
   - Keep package resolution locked to `Package.resolved` during test verification.
2. Create a committed, reproducible test invocation surface. Preferred implementation:
   - Share and commit the `RawCull` scheme under `RawCull.xcodeproj/xcshareddata/xcschemes/`.
   - Add shared test plans for the canonical release checks: `Smoke`, `Full`, and `Performance`.

   - Verify `xcodebuild -showTestPlans -project RawCull.xcodeproj -scheme RawCull` lists the committed plans from a clean checkout.
3. Add Makefile wrappers so docs do not need to expose Xcode-specific details:
   - `make test-smoke`
   - `make test-full`
   - `make test-performance`
4. Use exact `-only-testing:` identifiers as the current fallback selection mechanism:
   - Define the smoke subset by stable test identifiers.
   - Document that this is suite/identifier selection, not Swift Testing tag selection.
   - Keep `.smoke` and `.performance` tags in source as documentation and future-proofing, but do not claim the CLI filters by tag.
5. Keep Swift Testing source patterns and command-line execution patterns separate in the docs:
   - Source tags organize tests and may drive test plans when supported.
   - Makefile targets are the canonical command-line entry points.
   - Direct `xcodebuild` examples are allowed only when they use committed scheme/test-plan state or explicit `-only-testing:` identifiers.
6. Replace all documented `-testFilter` examples in `AGENTS.md`, `CLAUDE.md`, `RawCullTests/TEST_ARCHITECTURE.md`, and any related test docs.
7. Use these command shapes as the public contract, adjusted to the final plan/wrapper implementation:

   ```bash
   make test-smoke
   make test-full
   make test-performance
   ```

   Direct `xcodebuild` examples should include an explicit destination:

   ```bash
   xcodebuild test -scheme RawCull -destination 'platform=macOS' -testPlan Smoke

   ```

Acceptance criteria:

- No repository documentation recommends `-testFilter`.
- A clean checkout contains the shared scheme/test-plan or Makefile/script state required to run tests from the command line.
- Test documentation accepts Swift Testing conventions for new and updated tests: `struct` suites, targeted tags, `#expect`/`#require`, isolated fixtures, and parallel-safe test design.
- `find . -name "*.xcscheme" -o -name "*.xctestplan"` shows the committed scheme/test-plan files required by the documented commands.
- `xcodebuild -showTestPlans -project RawCull.xcodeproj -scheme RawCull` lists the intended committed plans.
- `make test-smoke` runs the intended quick validation subset and passes.
- `make test-full` runs the full test suite with Thread Sanitizer enabled and passes.
- `make test-performance` runs the intended performance subset or clearly documents why performance tests are manual-only.
- The same canonical commands are copied into `AGENTS.md`, `CLAUDE.md`, and `RawCullTests/TEST_ARCHITECTURE.md`.

## Priority 1: Correctness and Cancellation

These items directly affect user sessions with large catalogs.

### 4. Make Image Extraction Cancellation-Aware

Motivation:

The Sony/Nikon thumbnail and full-JPEG extractors still bridge to `DispatchQueue.global` through continuations. Once dispatched, ImageIO work keeps running even if the parent task is cancelled. For large ARW/NEF catalogs, this can waste CPU and memory after a user changes catalog, closes a zoom view, or cancels thumbnail generation.

Affected files:

- `RawCull/Enum/SonyThumbnailExtractor.swift`
- `RawCull/Enum/NikonThumbnailExtractor.swift`
- `RawCull/Enum/JPGSonyARWExtractor.swift`
- `RawCull/Enum/JPGNikonNEFExtractor.swift`

Plan:

1. Replace GCD continuation wrappers with cancellation-aware async wrappers.
2. Add cancellation checks before:
   - creating `CGImageSource`
   - scanning image-source indexes
   - decoding thumbnails or full previews
   - binary fallback reads
   - rerender/downsample work
3. Keep non-Sendable image objects local to the task that decoded them.
4. Add Swift Testing coverage for immediate cancellation and mid-flight cancellation where possible.

Acceptance criteria:

- Cancelling a thumbnail/full-JPEG request returns quickly where the decode has not already entered an uninterruptible ImageIO call.
- No `@preconcurrency` imports are introduced.
- Tests cover cancellation behavior for extractor wrappers.

### 5. Fix `ThumbnailLoader` Slot Accounting on Cancellation

Motivation:

`ThumbnailLoader.acquireSlot()` resumes cancelled waiters as if they received a slot, then increments `activeTasks`. The current caller usually balances this with `defer { releaseSlot() }`, but the invariant is fragile and easy to break.

Affected file:

- `RawCull/Actors/ThumbnailLoader.swift`

Plan:

1. Change slot acquisition to return whether a real slot was granted.
2. Do not increment `activeTasks` for waiters removed due to cancellation.
3. Keep pending continuation state explicit rather than using continuation resume as both "slot granted" and "cancelled".
4. Add tests for:
   - saturated loader
   - cancelled waiter
   - `activeTasks` never exceeding `maxConcurrent`
   - `cancelAll()` behavior

Acceptance criteria:

- Cancellation cannot over-admit work.
- Tests prove active slot count remains bounded.

### 6. Await In-Flight Sharpness Scoring Before Similarity/Burst Actions

Motivation:

`SimilarityGridSelectionView.runWithAutoScoring` checks whether scores are empty and then calls `calibrateAndScoreCurrentCatalog()`. If scoring is already active, `SharpnessScoringModel.scoreFiles(_:)` returns immediately. A second similarity or burst action can therefore proceed without waiting for the in-flight scoring prerequisite.

Affected files:

- `RawCull/Views/SimilarityGridView/SimilarityGridSelectionView.swift`
- `RawCull/Model/ViewModels/SharpnessScoringModel.swift`
- `RawCull/Model/ViewModels/RawCullViewModel+Sharpness.swift`

Plan:

1. Give `SharpnessScoringModel` an awaitable scoring operation.
2. If scoring is already in progress, return the existing task's value instead of returning early.
3. Make auto-scoring actions await the actual completion of scoring.
4. Disable or visually mark similarity/burst controls while the prerequisite is running.

Acceptance criteria:

- Rapidly clicking similarity and burst buttons cannot bypass scoring.
- Existing scores are reused.
- In-flight scoring is awaited exactly once.

## Priority 2: Memory and Cache Hardening

These items should reduce memory surprises during real catalog use.

### 7. Preserve the Current Cache Fixes and Add Tests

Motivation:

Current source has already improved two issues from the model review:

- `SharedMemoryCache.currentPressureLevel` is now lock-backed.
- `setObject` and `setGridObject` adjust manual cost/count counters when replacing an existing key.

These are good fixes, but they need focused tests so they do not regress.

Affected files:

- `RawCull/Actors/SharedMemoryCache.swift`
- `RawCull/Model/Cache/CacheDelegate.swift`
- `RawCullTests`

Plan:

1. Add replacement-accounting tests for memory cache and grid cache.
2. Add eviction-accounting tests through `CacheDelegate` where possible.
3. Add pressure-counter tests for warning, critical, and normal transitions through an injectable pressure handling path.
4. Keep synchronous cache reads documented because they rely on `NSCache` thread safety and lock-backed counters.

Acceptance criteria:

- Cache count/cost does not drift after replacement.
- Pressure level and pressure counters are thread-safe under TSan.

### 8. Keep Scan Preload From Competing With Interactive Grid Requests

Motivation:

`ThumbnailLoader.swift` has a TODO noting that 200px grid thumbnail requests can compete with scanning and thumbnail creation when grid/rated-grid views are open during preload. This is a user-facing responsiveness issue.

Affected files:

- `RawCull/Actors/ThumbnailLoader.swift`
- `RawCull/Actors/ScanAndCreateThumbnails.swift`
- `RawCull/Views/GridView`
- `RawCull/Views/RatedGridView`

Plan:

1. Prefer keeping the grid usable, but make request priority explicit:
   - interactive grid/loupe requests should outrank scan preloading
   - background preloading should yield under pressure
2. If a quick fix is needed for v1.7.6, temporarily disable grid/rated-grid navigation while initial thumbnail creation is active and show progress clearly.
3. Longer-term, split scan preloading and interactive demand loading into separate priority lanes.

Acceptance criteria:

- Opening grid during scan does not flood the same limited loader queue.
- Interactive selected-image preview remains responsive during preload.

### 9. Review Fire-and-Forget Cache Saves

Motivation:

`ScanAndCreateThumbnails` and `RequestThumbnail` encode JPEG data and then launch detached background saves. This is defensible, but cancellation and catalog boundaries are not explicit. Disk cache saves may continue after the catalog operation has moved on.

Affected files:

- `RawCull/Actors/ScanAndCreateThumbnails.swift`
- `RawCull/Actors/RequestThumbnail.swift`
- `RawCull/Actors/DiskCacheManager.swift`

Plan:

1. Decide whether cache writes should be awaited at operation boundaries or intentionally fire-and-forget.
2. If fire-and-forget remains, document the invariant: encoded `Data` only, no `CGImage` crossing, disk cache writes are harmless after catalog change.
3. Consider a disk-cache writer actor queue with cancellation or generation tokens.

Acceptance criteria:

- Cache-write lifetime is explicit.
- No non-Sendable image object crosses into detached save work.

## Priority 3: MainActor and Persistence Cleanup

These are lower risk than cancellation but improve Swift 6 maintainability.

### 10. Move Saved-Files Reads Off MainActor

Motivation:

`ReadSavedFilesJSON` is `@MainActor` and performs synchronous file I/O. `CullingModel.loadSavedFiles()` calls it synchronously during catalog load. For small JSON files this is usually fine, but it violates the project direction: UI-owned state should stay on MainActor, blocking disk I/O should not.

Affected files:

- `RawCull/Model/JSON/ReadSavedFilesJSON.swift`
- `RawCull/Model/JSON/WriteSavedFilesJSON.swift`
- `RawCull/Model/ViewModels/CullingModel.swift`

Plan:

1. Create a persistence actor or async persistence service for saved-file reads and writes.
2. Snapshot or return `SavedFiles` values, then apply them on MainActor in `CullingModel`.
3. Preserve debounced saves, but start the delay off MainActor if no UI state is touched before the first await.

Acceptance criteria:

- Catalog load does not perform saved-file disk reads synchronously on MainActor.
- Existing ratings, tags, sharpness scores, and saliency labels persist exactly as before.

### 11. Make Observable Model Isolation Explicit

Motivation:

`SettingsViewModel` and `MemoryViewModel` rely on project-wide default actor isolation instead of stating `@MainActor` on the type. The current build setting makes them MainActor-isolated, but explicit annotations make the intent robust and easier to audit.

Affected files:

- `RawCull/Model/ViewModels/SettingsViewModel.swift`
- `RawCull/Model/ViewModels/MemoryViewModel.swift`

Plan:

1. Annotate UI-facing observable models as `@Observable @MainActor`.
2. Keep CPU/system helpers `nonisolated` where they do not touch UI state.
3. Rebuild under Swift 6 to catch any newly exposed isolation issues.

Acceptance criteria:

- UI-owned models state their actor isolation directly.
- No behavior changes.

Acceptance criteria:

## Release Exit Criteria

v1.7.6 should not ship until all of these are true:

- `xcodebuild ... build` succeeds from a clean DerivedData path.
- The documented smoke test command runs and passes.
- Full test suite with Thread Sanitizer runs or any skipped tests are explicitly justified.
- A manual catalog load can be cancelled or switched without runaway thumbnail/JPEG work.
- Similarity and burst grouping cannot bypass required sharpness scoring.
- Memory diagnostics show no obvious cache counter drift during scan and grid browsing.
- `make build` produces a signed, notarized, stapled DMG.
