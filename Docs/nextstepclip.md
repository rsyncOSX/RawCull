## 8. Phase F: create the semantic relevance review set

The 77-query output has rankings but no ground-truth relevance labels. Raw cosine scores cannot replace human relevance judgments.

### F1. Review scope

Review the top five results for each query:

```text
77 queries × 5 results = 385 judgments
```

This is a practical first labeled benchmark. Expand to top 10 later if Precision@10 or a more robust nDCG@10 estimate is required.

### F2. Label format

Create a UTF-8 CSV with these columns:

```text
query_id,query,rank,score,file,path,relevance,notes
```

Use a three-level relevance scale:

| Label | Meaning |
|---:|---|
| 2 | Clearly relevant; directly satisfies the query |
| 1 | Partially relevant, ambiguous, or missing an important attribute/relation |
| 0 | Irrelevant |

Examples:

- Query `a dog`, image clearly containing a dog: `2`.
- Query `a red car`, image containing a car whose color is unclear: `1`.
- Query `a bicycle`, image containing only a wooden cart: `0`.
- Query `sharp portrait`, image containing a bird rather than a person: `0`.

Do not infer relevance from filenames or scores. Inspect the actual image.

### F3. Recommended local review artifact

Generate a local HTML review sheet containing:

- one section per query;
- the top five thumbnails in rank order;
- filename and cosine score;
- radio buttons or a simple field for relevance `0`, `1`, or `2`;
- an optional notes field; and
- export to the CSV schema above.

Keep image references local; the catalog and review artifact do not need to be uploaded or distributed.

### F4. Semantic metrics

Calculate at least:

- **Precision@1:** fraction of queries whose first result is clearly relevant. Decide before calculation whether partially relevant results count as zero or receive partial credit; report both if useful.
- **Precision@5:** number of clearly relevant results among the first five, divided by five and averaged across queries.
- **MRR:** reciprocal rank of the first clearly relevant result, averaged across queries.
- **nDCG@5:** graded ranking quality using relevance `0`, `1`, and `2`.

Also report metrics by query category:

1. Basic objects and scenes.
2. Color and other attributes.
3. Actions and relations.
4. Photographic quality and style.
5. Composition.
6. Counts, spatial relations, and negation.
7. Paraphrases.

The category breakdown is essential. A single average can conceal failure on relations, counts, negation, or photographic-quality concepts.

### F5. Semantic acceptance criteria

Define product targets before using the labeled results to approve a release. At minimum require:

- no unexplained universal hub;
- paraphrase overlap materially higher than unrelated-query overlap;
- acceptable Precision@1 for the primary user workflow;
- acceptable Precision@5 and nDCG@5;
- no production-critical category with clearly unacceptable performance; and
- manual review of representative failures.

Do not invent a threshold after seeing the results. If product targets do not yet exist, treat this first labeled run as the baseline and explicitly approve targets before the next run.

## 9. Phase G: build a labeled image-similarity benchmark

Semantic search and image similarity are separate product behaviors. They need separate labels and thresholds.

### G1. Pair categories

Build explicit positive and negative image pairs covering:

| Pair type | Expected use |
|---|---|
| Exact duplicates | Strong positive |
| Resized or recompressed duplicates | Strong positive |
| Exposure, color, or crop edits | Positive, depending on product definition |
| Adjacent burst frames | Near-duplicate positive |
| Same subject in a different photograph | Difficult boundary case |
| Semantically related but visually different | Hard negative for duplicate detection |
| Completely unrelated images | Negative |

Include difficult negatives. A benchmark containing only obvious unrelated images will produce an unrealistically optimistic threshold.

### G2. Pair-label schema

Create a CSV with:

```text
pair_id,image_a,image_b,pair_class,is_duplicate,is_near_duplicate,notes
```

Define `duplicate` and `near duplicate` in product terms before labeling. For example, decide whether a crop, color edit, or adjacent burst frame should be grouped automatically.

### G3. Similarity metrics and threshold selection

For every labeled pair, record the model cosine similarity. Then report:

- ROC-AUC;
- precision-recall AUC;
- recall at the chosen false-positive ceiling;
- false-positive rate at the chosen threshold;
- false-negative rate at the chosen threshold; and
- a confusion matrix for each proposed automatic action.

Select thresholds based on the cost of mistakes:

- A UI suggestion can tolerate more false positives than automatic deletion or grouping.
- Automatic destructive actions require a much stricter false-positive ceiling.
- A semantic-search cosine threshold must never be reused as a duplicate-detection threshold.

The corrected run reduced the previously false blue-flags/sunflower relationship from approximately `0.99765` to below the top-10 neighborhood range (below approximately `0.79` in that run). This is a strong integration improvement, but it does not by itself calibrate a production threshold.

- cold and warmed query latency; and
- nearest-image distribution, reciprocity, and threshold counts.

The corrected OpenAI baseline recorded in Section 1 has 53 distinct top-1
images, a most frequent top-1 count of four, and 418 unique images across all
top-50 results. Treat a return to the earlier universal-hub behavior as an
integration regression even if parity happens to pass.

These are diagnostic checks, not relevance labels. A diverse wrong result set
is still wrong.

### 15.15 Apply the shared human relevance labels

For each query, pool and deduplicate:

```text
OpenAI top five ∪ DataComp top five
```

Blind the model source where practical and apply the same `0`, `1`, and `2`
labels defined in Phase F. Calculate Precision@1, Precision@5, MRR, nDCG@5,
category-level results, and uncertainty estimates where supported.

Do not select OpenAI merely because it is the control model. Selection requires
acceptable labeled quality and understandable failures.

### 15.16 Compare image similarity on shared labeled pairs

Use the exact pair benchmark and product definitions from Phase G for both
models. For OpenAI report:

- duplicate and near-duplicate recall;
- hard-negative false-positive rate;
- precision-recall AUC;
- the selected operating threshold; and
- representative false positives and false negatives.

Do not reuse the DataComp cosine threshold. Each model needs independent
calibration even though both output normalized 512-dimensional embeddings.

### 15.17 Benchmark OpenAI operational cost and decide

Use the same hardware, OS, process state, catalog, warm-up, and measurement
procedure as DataComp. Record bundle size, index size, cold load, warm
P50/P95/P99 latency, indexing throughput, peak memory, and energy impact.

Fill the shared decision table in Section 14.17. Both models may remain user
choices if both meet the release gates. There is no requirement to declare one
universal winner: OpenAI may be preferable for one catalog while DataComp is
preferable for another. Document the default and the reason for it.
